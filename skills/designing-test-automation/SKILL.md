# 设计测试自动化

自动化购买反馈，不购买覆盖率表演。

## 选择反馈

按 `heuristic-testing` 定位项目 TCO 与当前 Spec 测试文档。当前 Spec 的自动化候选、实现位置、运行方式和证据写入其测试文档；只有形成跨 Spec 或长期反馈保护，或暴露项目级自动化薄弱面时才升级摘要到 TCO。

每个候选必须回答：

- 行为和 oracle 是否稳定到可以编码；
- 反馈频率或失败后果是否值得维护成本；
- 数据和环境是否可控且不会隐藏真实风险；
- 失败信号是否稳定并能区分原因。

选择能保留目标行为和 oracle 的最低层级。风险发生在真实边界时才跨边界。认知仍变化的内容继续探索，不急着固化。

## 第一条切片

```markdown
## 反馈需求
使用者 — 触发时机 — 当前延迟／损失

## 自动化目标
行为 — 层级／seam — 数据与环境 — oracle — 维护风险

## 暂不自动化
- 候选 — 缺少的稳定性或价值证据

## 第一条切片
最薄检查 — 实现位置 — 运行方式 — 失败证据
```

没有代码或环境访问权时，交付可直接实现的第一条切片。获得明确授权和访问权后，单元测试调用 `writing-unit-tests`；其他层级进入当前技术栈的实现流程。运行检查并处理不稳定因素；只有实际结果稳定且 oracle 有效，才称为已实现反馈。

**完成条件：** 第一条切片有明确使用者、触发、行为、seam、数据、oracle、运行方式和维护边界；实现状态与实际证据一致；实现细节和局部结果留在 Spec，TCO 只接收长期保护摘要。
