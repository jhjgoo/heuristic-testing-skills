# 项目测试产物路由

仅项目路径读取本文件。

## 两层产物

### 项目 TCO

每个项目只维护一份 `testing/TCO.md`。项目是共享产品目标、业务链、系统地图、风险清单和发布责任的测试范围，不机械等于 Git 仓库。

TCO 只保存长期认知：

- 测试使命、产品价值和关键业务链；
- 系统边界、接口、数据、状态、时间与运行条件；
- 稳定覆盖地图和节点 ID；
- 跨 Spec 或长期存在的产品风险、oracle、可观测性、回归与自动化薄弱面；
- Spec 索引、覆盖贡献和仍有效的残余风险。

项目地图不存在、失真或不足以判断变化影响时，使用 `mapping-project-test-space` 建立或刷新。单个变化的完整模型、TCON、用例和执行记录不得进入 TCO。

### Spec 测试文档

每个 Spec 只维护一份测试文档，承载当前变化的使命、影响面、风险、模型、TCON、可执行测试、执行证据、发现和残余风险。

优先沿用项目现有约定。没有约定时，在当前 Spec 包内使用 `test.md`；扁平 Spec 使用同目录同主体的 `-test.md`。找不到当前 Spec 的小修复在对话和测试代码中完成，不创建临时 Spec 或任务级 TCO。

批量数据或原始证据确实妨碍阅读时才拆文件，并由主测试文档保留摘要、稳定 ID 和链接。

## 写入顺序

1. 读取项目 TCO。
2. 读取当前 Spec、测试文档和新增证据。
3. 将当前变化的详细分析写入 Spec 测试文档。
4. 只把长期认知升级到 TCO。
5. 最终回复给出已更新文件的绝对路径、认知变化和下一步。

写 TCO 前只问：**当前 Spec 完成后，这条信息是否仍会改变项目后续测试？**

满足以下任一项才升级：影响多个 Spec；属于共享业务流程、系统、接口、数据或状态机制；重复出现并形成长期保护；改变项目级价值、风险、覆盖或测试投入。措辞严重、内容很多和当前优先级高都不是升级理由。

## 写入纪律

- 复用既有 Requirement、Scenario、Story、Task 和测试 ID。
- ID 稳定可读，不因排序变化重编号。
- 找到文件后原地更新，不另建“第二版分析报告”。
- 没有可写工作区时，在回复中交付应写入的完整内容，不伪造路径。

**完成条件：** 一个项目仍只有一份 TCO，一个 Spec 仍只有一份主测试文档；局部分析没有污染 TCO；长期认知具备升级依据；交付包含可点击路径、认知变化和下一步。
