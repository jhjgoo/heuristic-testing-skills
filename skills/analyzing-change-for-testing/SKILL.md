# 分析变化以支持测试

测试分析先于实施计划。它要暴露行为、规则、边界和 oracle，不替开发发明这些内容。

## 前置条件

读取 `heuristic-testing/references/artifact-routing.md`、项目 TCO、当前变化依据和已有 Spec 测试文档。

项目 TCO 不存在、失真或不足以判断影响时，先使用 `mapping-project-test-space`。不要用当前变化临时拼一份项目地图。

## 分析变化

### 1. 明确变化目的

用 `clarifying-test-basis` 确认用户任务、现状问题、产品承诺、成功信号及真实业务链。只问会改变范围、模型、oracle 或测试重点的问题。

### 2. 扫描增量影响

用 `scanning-product-with-sfdipot` 比较变化前后，指出受影响和明确不受影响的结构、功能、数据、接口、平台、操作和时间因素。追到上游触发、下游消费者、共享数据、状态、失败与恢复，不停在 PRD 页面。

### 3. 组织测试空间

用 `analyzing-test-space-with-mfq` 产出本次变化的能力、交互、质量特性和具体候选测试点。每项追溯到项目 TCO 覆盖节点或明确标为新节点。

### 4. 选择测试重点

用 `analyzing-product-risks` 比较产品价值落空与负面伤害，选择本轮高价值测试点。风险只负责选择范围、顺序和深度，不代替模型或测试条件。

### 5. 对复杂行为建模

流程、规则、数据、组合或状态复杂时，使用 `modeling-tests-with-ppdcs` 交付实际模型、覆盖准则、排除项和 TCON；简单行为直接形成 TCON。

以下任一项不同就拆分 TCON：前置状态、角色或权限、数据分区或边界、动作或刺激、观察位置、oracle、关联风险、测试层级或环境。每个 TCON 必须追溯到路径、规则、分区、组合或迁移。

### 6. 具体化当前轮次

只将本轮高价值 TCON 交给 `designing-test-experiments`。每个可执行测试必须写清状态、角色、数据、动作、观察位置和 oracle；其余 TCON 保留为后续候选，不批量展开。

## 实施前判定

只有同时满足以下条件，才写“测试分析足以支持实施”：

- 变化目的和业务结果明确；
- 业务链、系统、接口、数据、状态和时间影响明确；
- 高价值行为有实际模型，或有不建模的明确理由；
- 高价值 TCON 可追溯且已达到可执行程度；
- 实施计划无需发明产品行为、业务规则、边界或 oracle。

否则写“测试分析暂不足以支持实施”，逐项列出阻塞未知、证据来源、应答角色和它会改变的测试或实现。不要创建开发计划、ticket、分支或提交，也不要调用开发 Skill。

## 写入与交付

将变化影响、风险、模型、TCON、本轮测试、未知和判定写入当前 Spec 测试文档。只有跨 Spec 或长期有效的认知才升级到 TCO。

**完成条件：** 当前变化已从项目地图追到具体测试点、模型、TCON 和本轮可执行测试；实施前判定有证据；局部内容没有污染 TCO；最终回复给出测试文档、认知变化、判定和下一步。
